# ADR-0004 CI 重作业分流到局域网自托管运行机

- 状态：已采纳（负责人 2026-11-09 在对话中确认「启用 CI 分流」；运维线起草、编排审）
- 日期：2026-11-08
- 取代：ADR-0001 §2「部署、CI、对象存储、模型、Jev」行中「CI 用 GitHub 托管的标准 runner」的部分——改为「默认用 GitHub 托管的标准 runner；重作业可经开关分流到本 ADR 规定的局域网自托管运行机」。同一行「要 Docker 的 job 用 `ubuntu-latest`、不用 `ubuntu-slim`」对托管机仍然有效。
- 被取代：无
- 相关：ADR-0001 §2；`规划/11` §2.4（门禁从可信副本读）、§3.2、§4.4（门禁改动先问负责人）；代码仓库 `.github/workflows/ci.yml`、`tools/ci/check-workflows.ts`、`tools/ops/verify-container.sh`

## 1. 背景

- **托管机排队太久**：代码仓库是公开仓库，CI 一律跑在 GitHub 托管的标准 runner 上（ADR-0001 §2）。多条开发线并行之后，每张 PR 约有 20 个作业，托管机的并发被占满，单张 PR 常排队一到两小时，最多时排了 60 多轮。其中最重的是集成测试、属性测试、规则测试这几组，单个作业 30～40 分钟。
- **云上测试机已停用**：此前在云上开过按需测试机，负责人因费用全部停用（2026-11-01）。本机（开发用的 Mac）上的容器验证又受内存限制，多条线同时跑时会被系统杀掉（2026-11-08）。
- **负责人自备一台局域网 Linux 机器**：用来分流 CI 的重作业，同时接手本机的容器验证。

**为什么公开仓库不能简单挂一台自托管运行机**：任何人都可以 fork 后开 PR，PR 里的工作流定义由提交者控制。如果外人的代码在自托管机上跑起来，就能拿到那台机器，并以它为跳板进入局域网。

## 2. 决定

1. **默认不变**：所有工作流默认仍跑在 `ubuntu-latest`。仓库变量开关**不设或不等于开启值时，行为与本 ADR 之前完全相同**。开关可以随时一条命令关掉，不需要改代码。
2. **只接本仓库自己的代码**：只有两类运行可以排到自托管机：推送到主干，以及 head 分支属于本仓库的 PR。fork PR 一律走托管机。
3. **外部 PR 审批策略收紧**：仓库 Actions 设置改为「外部贡献者的每一个 PR 都要维护者批准才运行」。各开发线不批准外人的运行。
4. **一次性虚拟机**：每个作业在一台新建的虚拟机里跑，作业结束就销毁，不复用。
   - 运行机用一次性注册：一份注册只能接一个作业，用完即失效。
   - 能注册运行机的令牌只放在宿主上，只授权本仓库、只有管理运行机的权限，定期更换；虚拟机里没有任何令牌或密钥。
   - 虚拟机只能访问公网（代码托管、包仓库、系统源），访问不到局域网里的其他设备，也访问不到宿主。
   - 例外（2026-11-09 实测后补）：这台机器直连外网太慢或不通（2026-11-09 实测：GitHub 下载约 80 KB/s，Docker Hub 连不上，npm 超时；2026-11-11 更正，原写「直连 GitHub 不可用」），虚拟机的外网要经宿主上的代理。宿主只向虚拟机网段开放这一个代理端口，除此之外仍访问不到宿主；代理的节点订阅只放在宿主，虚拟机里没有。
5. **只分流重作业，分三批开启**：
   1. 属性测试；
   2. 规则测试与单元测试；
   3. 集成测试。
   
   门禁类检查、汇总作业、带写权限或读取密钥的作业，以及 `pull_request_target` / `workflow_run` 触发的工作流，**永远留在托管机**。合并门槛（必需检查的名称与判定）不变，不因作业跑在哪台机器上而改变。
6. **机械约束**：代码仓库的工作流检查脚本要拒绝下面几种写法：
   - 「自托管」字样出现在固定路由表达式之外；
   - 不该分流的作业或工作流被分流；
   - 分流作业的权限超过只读。
   
   这条检查本身属于门禁，按 `规划/11` §4.4 改动。
7. **回退**：一台监测脚本定期查自托管运行机是否在线，掉线就自动关闭开关、改回托管机，并通知编排。机器损坏或停用时，关开关即可，无需改代码。
8. **本机容器验证**：沿用已有的远程测试机做法：同路径同步工作树；数据库跑在主机沙箱里；整机同一时刻只跑一次。局域网机器的启用开关与已停用的云上测试机开关分开设置，互不影响。
   - 补注（2026-11-12 回写；编排裁定 D10-1237、D10-1241、D10-1334、D10-1336，代码仓库 CT-06zzzzu）：上面「整机同一时刻只跑一次」已不是现状。这台机器现在按槽位排队：2026-11-10 起有两个重槽，可以同时跑两份容器验证；2026-11-12 起另加一个轻量槽。重槽给 `--fast`、完整验证和 `--browser` 用，任务合并前的变基复验连同它自己的先红运行也占重槽；轻量槽只给单独跑的先红运行（`--red`）和开发过程中的测试用，先红运行排在前面。各槽里跑测试的容器都有内存上限，都不用 swap：重槽 9 GiB（带 `--browser` 的 12 GiB），轻量槽 6 GiB。每次开跑前先看宿主的可用内存：重槽要不少于这次运行自己的上限，轻量槽要不少于 8 GiB，不够就排队。这样做是为了不挤占同机的其他服务。先红运行换到轻量槽后，结论与证据不变；它在轻量槽里被内存上限杀掉时按环境错误处理，改到重槽重跑，以重跑的结果为准，不当作通过。这些槽位是按 CI 分流的虚拟机没有在跑来算的，重新开启 CI 分流之前先把重槽改回一个。轻量槽的个数与上限是试运行的取值，实测后可能再调。这里改的只是运行参数，本 ADR 其余各条不变；开发过程中的测试怎样交这台机器跑，见 `规划/11` §4.1。

## 3. 理由

- **为什么不加托管机并发**：要付费，而且同样会随开发线增多再次排满。
- **为什么不回到云上测试机**：负责人已因费用停用。
- **为什么用自托管**：本地机器是一次性投入，重作业正好又是最占托管机时长的那部分。
- **为什么边界不只靠路由表达式**：fork PR 能改自己那份工作流定义，路由写得再严也挡不住，只能算纵深防御。真正的安全边界是两层：
  - 平台层：外部 PR 必须经维护者批准才运行；
  - 隔离层：一次性虚拟机，不留状态、不带密钥、访问不到内网。
  
  两层各自独立，任何一层单独失守，都不会让外人代码拿到持久访问或内网访问。
- **为什么用虚拟机而不是容器**：集成测试本身要用 Docker 和管理员权限；在容器里跑，等于把宿主的管理员权限交了出去。

## 4. 影响

- **代码仓库**：要改以下几处，都属门禁与验证配置，按 `规划/11` §3.2、§4.4 先经负责人批准、走保护路径流程：
  - `ci.yml`：重作业的 `runs-on` 改为固定路由表达式；
  - `check-workflows.ts`：「每个作业都必须是 `ubuntu-latest`」改为本 ADR 的约束；
  - 对应的工具测试。
- **仓库设置**：外部 PR 审批策略收紧，由负责人本人操作。
- **运维**：
  - 局域网机器的系统安装与网络接入由负责人完成；初始化、虚拟机镜像、控制器与监测由运维线负责；
  - 令牌每 90 天更换一次，由负责人本人操作；
  - 虚拟机镜像每月重建一次，跟上运行机版本要求。
- **代价**：
  - 多了一台要维护的机器，也多了一个单点：它掉线时作业会排队，直到监测脚本把开关关掉；
  - 一次性虚拟机每个作业都要冷启动，并重新下载依赖，单个作业可能比托管机慢几分钟。
  - 虚拟机下载依赖走负责人的代理，流量计入他的代理套餐。第一批开启时实测每个作业的流量，并尽量在宿主上做缓存，用量过大时报负责人。
  
  以上几点在分批开启时实测，作业时长与失败率逐批报告。若不如托管机，就关开关回退。
- **不变的**：测试内容、合并门槛、门禁从可信副本读取的规则（`规划/11` §2.4）、只允许托管机运行的工作流，以及「Codex 生成的可执行内容不在宿主运行」的约定。

## 5. 实测（2026-11-09）

机器：i5-12400F（6 核 12 线程）、31G 内存、NVMe。用主干 e021095，在单个容器里跑，与同一时段 GitHub 托管机的作业时长对比：规则测试第 1 组 279 秒（托管机 1195 秒），集成测试第 2 组 598 秒（托管机 2754 秒）。这里只是裸容器的时长，不含一次性虚拟机的冷启动。
