## 1. 背景

### 1.1 负责人的质疑（D10-2213）

负责人 2026-11-20 15:29 对「余额缓存与分录不一致 → 开差错单 → 冻结 → 财务短信验证后手动重算 → 关单解冻 → 发站内信」这套做法提出质疑，要点（按编排在 D10-2213 里的转述，不是逐字原话）：

- 每一笔收入、扣减都有确定的来源：结算单是多少就是多少；提现后被联盟维权扣回、余额不够就记成负数；管理员调余额要带标识。
- 所以不存在「系统不知道哪个是对的」，不该靠差错单。

编排此前对负责人把这套流程解释成「系统不知道哪边对」，是说错了：08 BR-FUND-19 本来就写明以分录为准，余额只是分录的缓存。

### 1.2 复审结论（review.md ①）

1. 负责人的理解与规划、主干代码一致：每笔余额变动都是一条有来源、有类型、只增不改的分录；余额可以为负；余额就是分录加出来的数。
2. 「余额缓存 ≠ 分录合计」正常运行时不会出现，只可能由程序缺陷、绕过程序直接改库或分录数据丢失造成。前两种的答案是确定的（以分录为准），让人点一下不增加判断，还让用户多冻结几天；第三种恰恰是「以分录为准」会改错的情况，所以自动更正要带护栏。
3. 差错单不能整个取消：现在一种单据里装了三类事——与联盟、打款通道对不上的对账差异；规则要求有人批准才动钱的事项；系统内部自检发现的异常。只有第三类该把财务拿出来。
4. 2026-10-06 负责人确认的是「以分录流水为准修正余额」这一句；「由财务在差错单里点、要短信验证」是代理回写时比照「改余额要短信」补的细化。

## 2. 决定

### 2.1 题 1 = B：余额缓存不一致由系统自动按分录更正

系统发现某用户「余额缓存 ≠ 分录合计」时，系统自动按分录更正余额缓存：写审计（操作人记为系统，含更正前后的值）；可提现余额有变化时给用户发 BALANCE_CORRECTED 站内信（沿用负责人 2026-11-18 的决定）；告警。不开财务待办，不需要财务操作。

护栏——下面三条同时满足才自动更正：

- (a) 同一轮日终校验没有全局性异常；
- (b) 分录完整性检查通过（具体做法由工程定）；
- (c) 这一轮需要更正的账户数不超过上限（后台可配的小数；配置键由工程提，默认值待定，做成配置）。

任一条不满足：一个账户都不改，照原做法登记记录、冻结涉及用户的提现、全局异常时停月结入账，并发最高级别告警。被护栏拦下时保留「人工触发按分录重算」（短信档，原有写法）作兜底；后台不做「重算余额缓存」按钮。

「日结存表（daily_balances）缺行或不平」只告警并重跑生成，不冻结用户。

### 2.2 题 2 = B：其余内部自检异常称「账务自检异常」

BR-FUND-19 的 ②③④⑤⑥⑦⑧、入账后金额复核（证实核对）、收款侧自检的差异统称「账务自检异常」：

- 自动冻结相关用户提现、全局类自动停月结入账照旧；
- 告警给工程，由工程定位；后台单列一栏，不进财务待办；
- 需要动用户的钱时仍走 BR-FUND-24 人工调账；
- 同一个未解决的异常不再每天新登记一张、每天多加一条冻结。

### 2.3 题 3 = B：关闭会解除提现冻结的差错单要动态码

关闭一张「关闭会解除提现冻结」的差错单须动态码档二次验证，与后台人工解除冻结同档；不会解除冻结的关闭不需要。这与 08 BR-FUND-19 原文（关单时 step-up 解除）一致；原来矛盾的是 04 §11.2 `fund.recon` 行与 `design/specs/admin-recon.md` §5 写的「关闭不需二次验证」，本次改这两处，并在 08 写明档位。

### 2.4 编排的两点理解（已告知负责人，不是负责人确认）

1. 负责人 2026-10-04「修改账户余额需要管理员手机短信验证」只针对人工调账，不针对系统把缓存对齐到分录（没有人填金额）。所以自动更正不需要二次验证；人工触发的重算仍比照这句话归短信档。
2. 被护栏拦下的少数情况，保留已有的人工触发入口（短信档）作兜底；后台按钮不做，真遇到了再补。

### 2.5 没有定的（维持现状，本次不改）

- 题 4：月结时联盟结算数与我方按预估算出的数不一致怎样处理（BR-FUND-04 月结一致性校验）。未定，规则与流程参数不变。
- 题 5：「入账后只有预估佣金变化、结算数没变」是否仍出差错单（BR-FUND-01 R9b）。未定，不变。

## 7. 验收与恢复方式

验收（复审 ⑤ 的预发演练三条；规划/10 AC-S2-30 已按此改写）：

1. 给一个测试账户注入余额缓存偏差 → 下一轮日终校验自动更正，发站内信，有审计，有告警。
2. 注入超过上限的批量偏差 → 不更正，冻结，停月结入账（有全局异常时），告警。
3. 注入分录缺失（分录完整性检查不通过）→ 不更正。

另核：同一未解决的异常次日不新生成差错单、不新增冻结记录；关闭会解除冻结的差错单没有动态码被拒，不会解除冻结的关闭不要求。

恢复方式：

- 自动更正出问题时，把需更正账户数上限调到让护栏不通过的值（或用工程提供的开关，键名待登记），日终校验即回到「登记、冻结、告警」的原做法；人工触发入口（短信档）一直保留。
- 已经执行的自动更正有审计（含前后值）可查；确认是分录本身错漏的，按 BR-FUND-24 发 RECON_FIX 调账单补凭证，不直接改余额或分录。已发出的站内信不撤回。
- 规划文字的恢复：还原本次提交；08 各条的旧写法都登记在细则「取代」与例子的括注里。
