- 类别：00 §8 第 ② 类——资金计算的取数来源（结算佣金从哪来、何时写）与入账后扣回的开关默认值。

各项依据的文档写法：

- 京东 `payMonth`：文档说明是「当 payMonth 为当前的未来时间时，表示该订单可结算；为过去时间时，表示该订单已结算」，订单完成后才返回，默认 0。
- 京东 `actualFee`：推客分得的实际佣金。订单完成后发生退款，此金额会更新。
- 拼多多：`promotion_amount` 是唯一的佣金字段，含软件服务费；`duo_id_service_fee` 是软件服务费；order_status 5 = 已经结算。

规则的细节写的是**实测前按文档写法**的默认，下面几项都是代理补全的：

- 京东当日边界：`payMonth` 等于当日的不算已过；
- 京东 settled_at 取 `payMonth` 当日 00:00（+08:00）；
- 京东 `payMonth` 变回未来日期时走 P10；
- `actualFee` 的服务费扣法与 17 之后的预估相同。

这几项都挂在 V-49、V-50，实测结论不同的按 09 回填改 BR-FUND-02 细则。

## 5. 与现行规则的口径核对

逐条对过 08 现文，没有发现与现行 BR 的金额口径冲突：

- BR-FUND-02 原文就是「只在平台明确处于已结算状态时写结算佣金」。京东的已结算状态由文档对 `payMonth` 的说明给出；拼多多原文就认状态 5，只是没写取哪个字段。
- BR-FUND-04 ③ 原文就是「默认 api、upload 只作备用」。D10-529 让京东只能走 upload，本次是回到条目默认。
- 结算后佣金变化的处理全部走现有 R7 / R9 / R10 / R8，不新增迁移，也不改扣回、补差的金额算法。

有两点需要留意，都不是冲突：

1. 京东退件开关原文写的是「CAP-JD-08 实测确认字段含义后由运营打开（同 BR-ATTR-26『未验证能力不得据此处置用户资金』）」，这次由负责人决定提前默认开。`skuReturnNum` 的含义仍按 V-49 核对；入账本身仍受 `credit.enabled.jd` 与 08b 约束。
2. 任务里写的「按 R9 / R9b 路径扣回」：R9b 只存档、不扣钱。京东结算后 `actualFee` 既是预估也是结算值，降佣会同时写出新的结算记录，所以走 R10（负差即时）或 R9，不会落到 R9b。本记录按这个口径写。
