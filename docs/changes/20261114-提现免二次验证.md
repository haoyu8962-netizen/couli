# 用户提现不需要二次验证

- 日期：2026-11-14
- 类型：00 §8 第 ② 类（用户授权边界）。负责人在对话中明确决定，按 00 §8 直接回写并注明日期。
- 状态：规划仓库已写回（2026-11-14）；代码仓库的后续见 §5，由开发线认领。
- 决定人与原话：负责人 2026-11-14 在编排会话里当面决定，原话「用户提现 不需要二次验证了 因为用户已经登录了」。
- 编排裁定：D10-1665。
- 原状态：BR-ID-08、BR-WDR-01 都是「默认假设」（代理按依据补全、负责人未逐条签字），其中「提现须先取得 step_up_token」一句由本记录取代。

## 1. 决定

1. 用户在 App 里申请提现（`POST /v1/withdrawals`）不再需要 step_up_token（短信二次验证）。
2. 改收款账号（`PUT /v1/me/payout-account`）、更换手机号（`POST /v1/me/phone`）、申请注销（`POST /v1/me/deletion`）照旧需要二次验证。
3. `step_up_action` 的取值只剩 `payout_account_change`、`phone_change`、`account_deletion`。BR-ID-08 细则「绑定业务摘要」只剩收款账号变更这一种，提现的摘要（`w:<payout_account_id>:<amount_fen>`）一支去掉。

## 2. 不变的部分

- 提现仍只能由原生 App 发起；access_token 有效、请求签名与防重放、`Idempotency-Key` 照旧必须；`h5_token`、JSBridge、Agent 工具仍不得调用（BR-WDR-01）。
- 风控触发的加验照旧：BR-WDR-01 细则「旧手机号被二次放号时的提现加验」、BR-WDR-03 ③b 与 10010（契约 CT-26c）。
- 管理后台的二次验证完全不受影响：提现审核、驳回、执行打款、手动打款录入等仍按 BR-ID-34 要动态码或短信（BR-WDR-10、11、15、16、17）。
- 提现申请仍属「四个敏感操作」（提现申请、收款账号变更、换手机号、申请注销；原称「需要二次验证的四个操作」）：不登记 pending_action、补办后不自动重放、结果未知不换键、可确认或放弃、作废接口照旧适用（BR-ID-10 细则「不适用的动作」「敏感操作的幂等键」）。这一组的规则一条都没有放宽，只是改了叫法。
- 提现的校验顺序除去 ② 以外不变；限额、次数、手续费、税、状态机、分录都不变。

## 4. 影响

- **页面**：`Withdraw` 点【提交】后直接提交，不再弹二次验证；画板 `WithdrawStepUp-v2`、`WithdrawStepUpDark`（`design/specs/app-withdraw.md` §1「二次验证」「深色」两行）不再使用。收款账号页、换手机号页、注销页的二次验证不变。
- **接口与契约**：`POST /v1/withdrawals` 不再校验 `X-Step-Up-Token`、不再返回 10003；`POST /v1/auth/step-up`、`POST /v1/auth/sms-codes`（purpose=step_up）、`POST /v1/auth/oauth-attempts`（purpose=step_up）的 `action` 不再接受 `withdraw`；`POST /v1/idempotency-keys/abandon` 的 `action` 仍接受 `withdraw`（形状见 §5 第 3 项）。
- **历史数据与迁移**：不涉及资金数据；没有表结构变化。已核销的 action=withdraw 的 step_up_token jti 记录随令牌过期自然失效，不需要迁移。
- **新旧客户端共存**（编排定法，2026-11-14）：目前只有 staging，没有生产用户，三端与后端同版本落地即可，不做过渡期签发（后端不为 action=withdraw 继续签发 step_up_token）。D10-1666 已定的过渡期写法照旧：客户端收到 10003 仍弹面板，取提现令牌时不带摘要。`POST /v1/withdrawals` 忽略请求头里的 `X-Step-Up-Token`，不校验、不核销。
- **验收用例**：10 AC-S2-20、AC-S2-62、AC-S2-80、AC-S1-83；01 F-ACC-07（AC-ACC-07）不变，只对应其余三个操作。
- **客服话术**：用户问「提现要不要验证码」时答不需要；收款账号变更、换手机号、注销仍要。10003 的文案（BR-TEXT-14 表 A）不变。
- **风险**：提现只凭登录态。别人拿到已登录的设备时可以直接发起提现，但收款账号只能是本人已绑定、户名与实名一致的账号（BR-WDR-02），改收款账号仍要二次验证，所以钱只会到账号主人自己的收款账号；旧手机号被二次放号的情形由风控加验兜底；每日、每月次数与金额上限、自动到账规则组与人工审核（BR-WDR-04、BR-WDR-30）不变。

## 5. 代码仓库的后续（由开发线做，不在本 PR；第 7 项设计说明已随本 PR 同步）

1. 后端：`POST /v1/withdrawals` 去掉 step-up 校验与令牌核销；提现建单锁内的业务摘要比对一并去掉。与三端同版本落地，不做过渡期签发（§4）。
2. 契约：`StepUpAction` 去掉 `withdraw`，删除 `StepUpSummaryWithdraw`（`POST /v1/auth/step-up` 的提现摘要）；`POST /v1/withdrawals` 去掉 `x-step-up` 标记与 `X-Step-Up-Token` 头。
3. 契约（连带）：作废接口 `POST /v1/idempotency-keys/abandon` 的 `action` 原引用 `step_up_action`，去掉 `withdraw` 后要另立一个取四个值（withdraw、payout_account_change、phone_change、account_deletion）的枚举，否则「放弃上一笔提现」用不了。
4. 契约与三端（连带）：凡是靠 operation 上的 step-up 标记识别「四个敏感操作」的地方（03 §4.2 `ErrorActionMapper` 的不自动恢复判断、幂等记录不按 30 天清理的范围、作废接口按 action 定位 method 与 path、版本闸门对作废接口的判定），提现去掉 step-up 标记后要改用单独的标记或清单，提现申请不能因此掉出这一组。
5. 三端：提现流程不再弹二次验证（`StepUpSheet`），提交请求不带 `X-Step-Up-Token`；收款账号页、换手机号、注销照旧。
6. 测试：AC-S2-20 ⑦ 改为断言提现不要 step-up；收款账号变更缺少、过期、action 不符的 step-up 仍返回 10003 的用例保留或补上。
7. 设计：设计说明已随本 PR 同步——`design/specs/app-withdraw.md` 加 2026-11-14 同步说明，规则引用、资金页标注、§1「二次验证」「深色」两行、§2「提交」行、§3「二次验证」文案键行、§4 `sendSmsCode / stepUp` 与 `createWithdrawal`（去掉 10003）两行、§6 证据稿一句、§7 业务摘要缺口一项改为本页不用或删去；`design/brand/preview.js` 提现预览（`screenWithdraw`）说明里「以及二次验证」一句去掉。没改的：`design/README.md`「App 内高保真第 2 批定稿」里 `WithdrawStepUp-v2.dc.html`、`WithdrawStepUpDark.dc.html` 的定稿登记（文件名与 sha256）是负责人定稿时的历史记录，画板本身也留在 couli-runs 不删，只在 `app-withdraw.md` 标为本页不用；收款账号变更、换手机号、注销的二次验证画板与说明不受本次决定影响，也不改。

## 6. 验收与恢复

- **验收**：已登录用户在原生 App 提现，点【提交】后不出现二次验证，请求不带 `X-Step-Up-Token` 也能建单，不返回 10003；改收款账号、换手机号、申请注销仍要二次验证，缺少或过期的令牌返回 10003；被打标的旧号账号提现仍返回 10010；后台提现审核与打款仍要二次验证；h5_token、JSBridge、Agent 调用提现接口仍被拒；「放弃上一笔提现」仍可用。
- **恢复**：负责人要恢复提现的二次验证时，把提现重新加回 BR-ID-08 正文的动作清单与 BR-WDR-01 正文的条件（action 恢复为 {withdraw, payout_account_change}）、恢复 BR-WDR-03 ②，04 §2.5 `step_up_action` 加回 `withdraw`、§5 step-up 行与 §6.4 鉴权列恢复「S I + step-up」，BR-ID-08 细则「绑定业务摘要」的提现一支按需恢复，并同步 §3 表中各处；代码侧按 §5 反向处理。「四个敏感操作」的叫法可以保留，不影响恢复。
