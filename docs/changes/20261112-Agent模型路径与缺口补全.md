## 1. 核对结论

### 1.1 现在线上实际是什么样

1. 模型路径没有接通。装配里路由固定为无模型、提示词固定为空，没有配置或环境变量能打开；私有库里没有提示词，仓库里没有路由文件、同意厂商清单、模型 Key 的读取位置。

3. 输入审核没有凭据时每条消息都被拒答。按 2026-11-04 三端联调时的核对，staging 的阿里云内容安全凭据还没有放（负责人 2026-10-22 已定开通），`agent.enabled` 也关着，所以 staging 上的 AI 助手实际不可用，三端没有连过真实后端。11-04 之后有没有变化这次没有登录 staging 核实。

## 2. 设计补全

### 2.1 上下文块与追问改条件

- **内容**：模型每一轮收到固定的系统提示词与工具定义、服务端代码生成的上下文块、本条用户消息。上下文块含当天日期、情境入口出的卡、当前商品结果、当前搜索条件、最近若干轮（上限见 BR-AI-05 细则）的用户原话与服务端记下的动作；不调用模型写摘要，更早的轮次不带，不回放助手说过的文字，不出现商品价格、返利与订单状态（用户自己说的价格条件可以出现）。历史里的用户原话要按发给模型的形式再处理一遍（去掉链接与口令；长数字写成不带序号、不能还原的记号，模型不能拿它当订单号用）。只收「输入已通过」的轮次：这一事实随终态同步落库（`agent_runs.input_passed`），输入被拦、被拒答、审核出结果前就结束或崩溃的轮次都没有这个标记，不进上下文块。给模型的商品编号是每件商品自己那张卡的编号。在已有结果上改条件由模型输出 refine 意图，可改的条件与 `search_products` 的模型可给参数相同，没改到的条件原样保留。取代 02 §9.2 原写的「保留最近 8 轮原文，更早的摘要 ≤300 字」。
- **涉及的 BR**：BR-AI-05 细则新增「上下文块」「追问改条件」；BR-AI-07（相对日期）、BR-AI-19、BR-AI-20、BR-AI-22 为依据，不改。
- **受影响的页面与接口**：无对外接口变化。代码仓库 agent 模块的编排核心与结果集；`agent_runs` 加一列 `input_passed`（04 §3.2）；配置 `agent.context.max_turns`、`agent.context.max_chars`。
- **验收**：规则测试钉住上下文块的五项内容与不得出现的内容（历史轮里没有链接、口令和数字尾号，被拦的轮次、审核出结果前被取消或崩溃的轮次不在其中）；评测多轮指代类达到 BR-AI-21 的门槛。
- **恢复方式**：把 `agent.context.max_turns` 设为 0 即不带历史（回到只有当前一句）；规则回退则改回 02 §9.2 原句与 BR-AI-05 细则。

### 2.2 提示词的结构与来源

- **内容**：提示词放私有库不变。结构分冻结区与可变区，可变区条款带编号；公开仓库只放加载器与版本引用，加载器核对哈希与长度，对不上按无模型降级运行并告警；当天日期等会变的内容不进系统提示词。第 1 版草稿由本次规划会话起草，放在本机运行目录，由 agent 线核对主干的工具定义与意图形状后写进私有库。
- **涉及的 BR**：BR-AI-21（依据，不改）。02 §9.2「前缀缓存」「Prompt 管理」两行各补一句。
- **受影响的页面与接口**：无。
- **验收**：加载器的规则测试（哈希不符、超长、读不到时按无模型运行）；冒烟集回放通过。
- **恢复方式**：路由切回无模型。

### 2.3 情境入口

- **内容**：从商品详情、订单详情点「问问 AI」进入对话页不自动发送，用户发出的第一条消息带 `context`，只接受 App 内这两处带来的。服务端先做输入审核，再按入口出卡：商品走确定性路径出报价卡，之后用户打的字照常处理（无模型时到出卡为止）；订单按查订单出订单卡与模板文字，本轮到此为止。剪贴板文字首版不走 `context`：识别结果卡上的「让 AI 帮我看看」只打开对话页，要问的内容由用户自己粘贴后作为消息正文发出，服务端收到 `context.text` 时不读取、不落库、不交给模型。`context` 形状不合法的请求照契约按 20001 拒绝。08 BR-AI-01 细则原「边界」一句、BR-ID-10 细则一句与 03 §7.5 原写「自动发送首条消息」，安卓、鸿蒙的实现是不自动发送，统一为不自动发送。
- **涉及的 BR**：BR-AI-01 细则新增「情境入口」，「边界」一句改写；BR-AI-07 细则「问问 AI」一句同步；BR-ID-10 细则「路由入口矩阵」AgentChat 一句改写并写明 `context` 的来源限制；BR-ID-16（剪贴板原文不上传）为依据，不改。
- **受影响的页面与接口**：`POST /v1/agent/sessions/{id}/messages` 的 `context`（契约形状不变）；01 §4 情境入口与 F-CLIP-04、02 §9.2、03 §4.4 与 §7.5、10 AC-S1-81 ⑩（桥带来的 `context` 被丢弃）；商品详情、订单详情的「问问 AI」。
- **验收**：10 AC-S1-189；规则测试覆盖两种入口、身份限制、订单工具关闭、订单不在名下、消息自身带链接、`context.text` 被忽略、形状不合法返回 20001。
- **恢复方式**：服务端忽略 `context`（回到现状）。

### 2.4 意图兜底与不空回复

- **内容**：模型给了意图却没调工具时，服务端按意图代调只读工具（查订单取默认的时间范围，有订单号占位符时按单号查、平台取用户这句话里点名的；查收益；规则检索；客服卡；找货按关键词搜索），身份限制不变，照常计入单轮工具调用上限与按单号查询的每日上限。以 stop 或 limit 结束的回复不得为空，空了补 `agent.reply.empty` 与 3 个快捷问法；只出了 notice 卡不算空。
- **涉及的 BR**：BR-AI-01 细则新增「意图兜底与不空回复」；BR-TEXT-22 新增 `agent.reply.empty`、`agent.suggest.empty.1–3`。
- **受影响的页面与接口**：对话页多一种兜底文字与快捷问法；配置 `agent.orders.default_span_days`。
- **验收**：规则测试覆盖六种意图的代调、游客与未绑手机仍出登录或绑手机卡、空白输出的兜底。
- **恢复方式**：去掉代调（回到现状的空回复）不可取；只恢复规则文字时把 BR-AI-01 细则这一段删去。

### 2.5 无模型降级先按问法分流

- **内容**：无模型时（现在线上、模型故障、预算用完）先分流——问页面在哪、问一般规则、问本人订单、问本人收益、要人工——都不是才做关键词搜索，并用代码规则取出价格条件、平台、排序说法与排除词。分流用一套单独的、偏严的判别，拿不准按找货处理；不沿用核对模型标签的那套判别（那套会把「哪个返利最高」判成规则、把「钱包多少钱」判成查收益）。分流之前只先看有没有排序说法；点名了平台、带了价格都不单独算找货（否则「我的淘宝订单返了吗」会被拿去搜商品），平台与价格只在搜索时当条件取出。规则里给了必须分流与不得分流的两组例句。同时修三处：检索词不带不可信定界的标签与长数字占位符；只有问候语时不搜索、回欢迎语（没有商品词的话如「这个多少钱」也不搜索，回兜底的那句）；结果全被禁售类目过滤时用禁售话术。不依赖模型的消息（含链接或口令的、分流到的五类、无模型时的情境入口）结束原因照常，不因模型不可用改成 fallback / budget。
- **涉及的 BR**：BR-AI-14 细则「无模型降级」的做法改写（已确认规则的细则，第 ② 类）；BR-AI-16 正文在「finish_reason=budget」后加一句指针。
- **受影响的页面与接口**：对话页在无模型时的回答；`done.finish_reason` 的取值范围不变；开关 `agent.degraded.route_intents`。01 F-AGENT-13、02 §9.2、§14 摘要同步。
- **验收**：规则测试覆盖两组例句与六步；10 AC-S1-57 的第三、四组；staging 不接模型时七类问法各得到对应的卡片或话术（02 §9.4 第 1 步的完成标志）。
- **恢复方式**：`agent.degraded.route_intents` 设为 off（三处修正不随它回退）。
