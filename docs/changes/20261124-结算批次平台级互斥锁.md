## 1. 现状与问题

「发起补充」生成补充批次与批次执行器执行入账可以同时跑。B2-04rd 三轮资金评审的共同缺口是：补充在读「哪些订单已入账」与写补充明细之间，执行器可能正好把同一批订单入账，现有的订单键锁只能逐单互斥，挡不住「生成侧读了一批、执行侧在其间入了其中几单」。

## 2. 决定

BR-FUND-16 细则「加锁流程」在第 1 步之前加第 0 步，只对结算批次生效：

- 执行入账的明细事务先取所属平台的结算互斥锁（咨询锁，事务级）的共享模式；
- 生成批次的事务（发起补充，以及月结账单日任务）先取同一把锁的排他模式；
- 两侧都在取任何订单键锁之前取这把锁，持有订单键锁时不再等它，所以不成环；
- 其余记账事务（扣回、补差、恢复、提现类）不取这把锁，原有顺序不变。

## 3. 影响评估

- 业务规则：只动 BR-FUND-16 细则「加锁流程」一处；正文、其余 BR 不变。
- 行为代价：财务点「发起补充」的那一刻若正有批次在执行入账，执行会停顿到补充生成完（平时几秒，一次补几万单时可能几分钟）；反过来补充要等在途的那一条明细事务提交。不改任何金额结果。
- 页面与接口：无新增、无形状变化；不需要负责人提供新资料。
- 代码仓库：任务 B2-04re（取代 B2-04rd，B2-04rd 置 void；发起补充与月结账单日任务两处的排他锁都在本单做）；`apps/api/src/modules/settlement/AGENTS.md` 的取锁顺序一句同步（保护路径，伴随小单、带负责人标签）；新锁键登记进锁键台账（FU-ADVISORY-LOCK-KEY-REGISTRY）。取到共享锁之后、入账之前再核一次入账开关（BR-FUND-04 ⑦ 的 10 秒要求），关了就不入这一条。
- 已知残余（接受）：扣回、补差审批、平台恢复三类事务只取订单键锁，补充放掉某块订单键锁到提交之间它们若提交，本轮可能多出一条指向已关闭义务的补记项（执行时锁内重验跳过）或漏一条新开的义务（下轮补上），不动钱。

## 4. 验收

- 并发用例：补充生成期间没有入账明细事务提交（执行侧等补充生成完，补充按对方提交后的状态出补记项）；两侧互等不死锁。因入账开关暂停的批次里的单仍可进补充批次，之后哪边先执行哪边入账、另一边执行时按「不在待入账」跳过——这条现有行为不变。
