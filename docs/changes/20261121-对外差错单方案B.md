## 1. 背景

### 1.1 负责人的出发点

返利金额跟随联盟订单接口：未结算前随联盟变更自动变更；差错单流程不应把系统逻辑缺陷转成人工逐单调账。

### 1.2 复审结论（复审 ①、③、④、⑥）

1. 「联盟变，我们跟着变」规则本来就是这么写的：入账前按联盟数据重算；入账按联盟结算额；入账后负差同事务自动扣，正差按批次批准（BR-FUND-04 ①⑦、BR-FUND-09 ①②）。金额差几块不会出联盟对账差错单。
2. 联盟对账差错单（`union_mismatch`）只在「联盟结算了我方状态不对的单」时出现（BR-FUND-09 细则「差错单类型」）。这类单每一种都有订单级出口；用 RECON_FIX 调账给订单补钱或扣钱，凭证键是 `ADJ:{adjust_id}`、不挂在订单上，BR-FUND-08 的已入账净额也不含它，之后这单再扣回或补差时系统看不到这笔钱。
3. 通道对账差错单（`channel_mismatch`）上真正需要动钱的，是支付宝那边确实多付了钱（迟到成功、重复付款）。钱付没付、付了多少要人看账单确认，系统不能自己判，但可以把单子填好。
4. 同一张差错单被重复提交调账，现在没有防护：主干代码调账只校验差错单存在、不是 R4，不读也不改差错单状态（复审 ④ ⑥）。

## 2. 决定（D10-2317 ②，取复审 ⑤ 的方案 B）

1. **联盟对账差错单**：后台不出【去调账】，改为订单级处理入口——按订单走已有的手动同步、补充批次、订单恢复（R12 / R13）与结案。
2. **通道对账差错单**：只有确有多付时，系统预填一张 PAYOUT_RECOVERY 待批追回单，财务核对账单后确认；不是自由填写的调账。
3. **关联差错单的调账执行**：同一事务内把该差错单用 CAS 置为 adjusted；差错单已不在 open / processing 即返回 20902；一张差错单至多对应一张「已执行且未红冲」的调账单。

F1-08ee 的【去调账】部分在本记录合并前继续暂停，【申诉恢复】部分照旧（D10-2317 ②、D10-2318）。

## 7. 验收与恢复方式

验收（规划/10 AC-S2-114，AC-S2-50 ④ 已按此改写）：

1. 联盟对账差错单：详情不出【去调账】；由人发起、关联它的调账单被拒，不写凭证。
2. 通道对账差错单（内部 FAILED 已退回、支付宝成功）：登记时已有一张待批追回单，用户取自提现单、金额只读；批准后同一事务差错单为 adjusted、写 ADMIN_ADJUST，冻结仍在。
3. 同一差错单的第二张调账单执行 → 20902（`data.resource=recon_diff`），不写凭证；两人并发批准同一张预填单只生效一次。
4. 内部已付而支付宝没有记录的通道对账差错单：调增预填开关关（默认，待负责人确认）或 BR-TEXT-19 未给调增定出用户侧说明时不预填、不出调账入口；两者都满足后预填调增单（§5-5）。另：涉及两个受益人的日终子订单差错单，两人各调一张后才置 adjusted（§5-14）。
5. 红冲该追回单后差错单回到 processing。

恢复方式：

- 规则层：预填单是待批的，有问题不批准、驳回即可，不动钱。已执行的追回单按 BR-FUND-24 整笔红冲，红冲同时差错单退回 processing。
- 实现层：B2-17 出问题时，可回退「系统预填」一段（不再生成预填单，差错单照旧冻结、待处理），CAS 与唯一约束保留（它们只拒绝、不动钱）。
- 规划文字：还原本次提交；各条旧写法登记在 BR-FUND-24、BR-WDR-23 细则的「取代」与 `design/specs/admin-recon.md` §7 的原写法一句里。
