## 1. BR-FUND-04 ④：一次出账的重生成上限

- **内容**：
  - 一次出账（月结账单日任务或一次后台补充）里，「重生成成功、订单锁留到事务提交」的子订单最多 500 张。它是技术常量，不进配置，与补充候选分块的张数同值同理由。
  - 只数重生成成功的：金额本来相符的不取锁、不占名额；重生成失败或重生成后仍不一致的回滚放锁，也不占名额。
  - 超过上限的子订单本轮不重算、不取锁、不入批、不登记差错单、不发工程告警，保持 WAITING，留给下一次对同一账单发起补充时接着处理（每次最多再 500 张）。
  - 本次留下的张数单独记为账单的「待下次重算」数，让财务在后台看得见；不并进「暂缓」数，「暂缓」仍只指人工暂缓与维权中的订单。
- **起因**：B2-18 资金评审第 5 轮第 1 条 S1。每张重生成成功的订单要持锁到整次出账提交，一次几千张会占满数据库锁表，后面的订单反而处理不了。依据 couli-runs `B2-18/regen-cap-note.md`。
- **代价**：金额不一致的订单很多时要分几次补充（例如积压 2000 张要补充 4 次）；平时只有零星几张，碰不到上限。
- **涉及的 BR**：BR-FUND-04 正文 ④、细则参数表加一行「一次出账的重生成上限」、校验结果表「差额超出容差」行、细则「取代」。
- **受影响的页面与接口**：
  - 代码仓库 B2-18：bill/follow-union、月结任务、补充发起这三处加上限与「留到下次」的结果。
  - 「待下次重算」数要动接口与后台账单页，不在 B2-18 的可改路径内，另登跟进单：后端加列与接口字段、前端显示，可与「应结未结」「金额不一致」两个尚未接上的计数一起做。
  - 在那之前，B2-18 先把这个数落在日志事件与批次 / 账单上现成可放的字段里，不只存在内存。
- **验收**：重生成成功到 500 张即停；超出的保持 WAITING、无差错单、无告警；下一次补充接着处理；「待下次重算」数写对且不计入暂缓数；金额相符与重生成失败的单不占名额。
- **恢复方式**：去掉上限常量，回到一次出账内全部重生成；回退 BR-FUND-04 的相应句子。没有数据迁移（「待下次重算」若已加列，留着不读即可）。
- **未核实（如实写）**：生产数据库的锁表参数尚未建实例。staging 实测为 250 / 250，不是 PostgreSQL 默认的 64 / 100；上限按默认值保守取 500。

## 2. BR-AI-16：AI 日预算取「甲」

- **内容**（逐句依据 couli-runs `B3-09m/br-ai-16-draft.md`，取向见 `B3-09m/owner-options.md`「甲」）：
  - 受理 run 时的预占额同时是该 run 的花费上限。每次模型调用前按「最多可能花多少」检查，放不下就不再调模型、本 run 按预算用完收尾。发给厂商的输出上限按剩余额度算，小于 256 不调。
  - 一个 run 的全部成本记在受理日。正常收尾按实际冲正；没能正常结束的（崩溃、别处收尾、结果不明）按预占记满。
  - 80% / 100% 告警尽力而为，可能重复或晚到，不作熔断条件；熔断只看受理时已提交的累计。
  - 单价受理时取定，整个 run 只记一个版本。
  - 预占额 `agent.budget.reserve_mfen_per_run` 默认 1,000 → 5,000 mfen，键名不变。
  - 超支上界：一天的真实花费 ≤ 上限 + 一个预占额，再加跨零点部分；跨零点新一天少记的量 ≤ 零点进行中 run 数 × 预占额。
- **被取代的要求**（细则「取代」逐条保留原文）：调用完成日记账；允许单个 run 超出预占；80% 告警当天一次（代码仓库曾要求两档各恰好一次）；trace 每次调用记单价版本；默认预占 1,000 mfen。代码仓库里随之作废的实现口径也列在同一条「取代」里：调用前登记与待定成本、调用完成即入账、跨日冲正分日、失败尝试撤登记、输出上限常量 32768、跨 app 合成单价版本。
- **涉及的 BR**：BR-AI-16 正文与细则（状态、默认值、取代、预占、单价、W 与输出上限、U 的累加、两步记账、告警、超支上界、例）；同主题「本主题未决问题」第 8 条的预占额。BR-AI-14「无模型降级」引用「日预算用完」仍一致，未改。

  - 没有新增接口与错误码；done.finish_reason=budget 不变。
